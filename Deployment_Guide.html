The assessment creates one read-only IAM role from a CloudFormation template, runs a collector that reads configuration metadata through that role, and writes one HTML report. It reads no data, changes nothing, installs nothing and sends nothing outside AWS. The customer can remove the role at any time (Removing access).

Before you start (every path)

Where the bundle comes from: DataProtectionReview_Bundle.zip is the file your partner sends you, and this guide is one of the files inside it. Keep the zip itself: it is what you upload to CloudShell below. (Partners build it from the repository with python tools/make_bundle.py, which writes output/DataProtectionReview_Bundle.zip.)

  1. Sign in to the AWS Console as someone allowed to create IAM roles and CloudFormation stacks. For an organization, sign in to the management account; the same person must be allowed to create a StackSet and to turn on StackSets for the organization (the organization command does that, once).
  2. Check who will run the collector. The collector reads each account by assuming the read-only role there, so the person running it needs permission to call sts:AssumeRole on that role (on the role in every account, for example arn:aws:iam::*:role/DataProtectionReviewer). Administrators usually have this. A restricted permission set, or a session policy on a single sign-on session, can leave it out; the run then stops with an access-denied message (see "The collector cannot assume the role" below).
  3. Open AWS CloudShell (the >_ icon at the top of the console). It already has the AWS CLI, Python 3.9 and the AWS library the collector uses. Nothing else to install.
  4. Upload the bundle: Actions → Upload file → DataProtectionReview_Bundle.zip. Then paste:
unzip -o DataProtectionReview_Bundle.zip

The quickest way: one command

Easiest: run this with no options. It asks the customer and partner names, what to assess (this account, the whole organization, or the member accounts only), whether to include Cost Explorer, and which Regions to scan. It shows the plan and creates nothing until you say yes, then runs the assessment and zips the results into one file to download.

bash run.sh

The commands below do the same without the questions.

Run one of these in CloudShell, in the folder you unzipped. Each one does everything the steps below do, in the same order, and prints each AWS command before it runs it: it creates the read-only role, makes the External ID for you, checks access, runs the assessment and tells you where the report is.

bash run.sh account

One account. Or, for an organization (sign in to the management account):

bash run.sh org

An organization where you cannot create a role in the management account (the roles go into the member accounts only; see "If you cannot create a role in the management account" below):

bash run.sh org --no-management-role

Add --org-name "Customer name" --partner-name "Partner name" for the report's header and footer, unless the person who sent you the zip already set them. The External ID is saved next to the script in .external_id, so running it again reuses it and does not break the roles already created; it is printed at the end too. --external-id uses one you give, and --output-dir chooses where the report goes. The person running it needs permission to create the stack and to assume the role it creates (sts:AssumeRole). The steps below do the same thing one command at a time, for when you want to see or change each one.

Single account

Paste each line into CloudShell, in order, in the same window.

1. Set the names and the External ID

Change the two names in quotes first. They appear in the report's header. The line then makes a new External ID, finds the IAM role or user you are signed in as (who the role will trust), and picks the role's name. It is safe to run again: an existing DataProtectionReviewer stack is updated in place with the name it already has, a failed earlier attempt is removed first, and if a role of that name exists that no stack here created, the new role gets its own name (DataProtectionReviewer- and six letters or digits) instead of touching the existing one.

ORG="Customer name"; PARTNER="Partner name"; EXT=$(python3 -c "import secrets; print(secrets.token_hex(24))"); ME=$(aws sts get-caller-identity --query Arn --output text); case "$ME" in *:assumed-role/*) ME=$(aws iam get-role --role-name "$(echo "$ME" | cut -d/ -f2)" --query Role.Arn --output text);; esac; echo "Role will trust: $ME"; ROLE=DataProtectionReviewer; read -r ST R <<< "$(aws cloudformation describe-stacks --stack-name DataProtectionReviewer --query "Stacks[0].[StackStatus,Parameters[?ParameterKey=='RoleName'].ParameterValue|[0]]" --output text 2>/dev/null)"; if [ "$ST" = ROLLBACK_COMPLETE ]; then echo "Removing a failed earlier attempt"; aws cloudformation delete-stack --stack-name DataProtectionReviewer && aws cloudformation wait stack-delete-complete --stack-name DataProtectionReviewer; ST=; fi; if [ -n "$ST" ]; then [ -n "$R" ] && [ "$R" != None ] && ROLE=$R; echo "Updating the existing stack"; elif aws iam get-role --role-name "$ROLE" >/dev/null 2>&1; then ROLE="DataProtectionReviewer-$(python3 -c "import secrets; print(secrets.token_hex(3))")"; echo "A role named DataProtectionReviewer exists outside this stack, so this one is named $ROLE"; fi; echo "Role name: $ROLE"

2. Create the read-only role

aws cloudformation deploy --stack-name DataProtectionReviewer --template-file data_risk_assessment_role.yaml --capabilities CAPABILITY_NAMED_IAM --parameter-overrides TrustedPrincipalArn="$ME" ExternalId="$EXT" RoleName="$ROLE" && echo "ExternalId: $EXT"

Keep the External ID it prints. It is not a secret, but a later run needs it.

3. Run the assessment

python3 collector.py --external-id "$EXT" --role-name "$ROLE" --org-name "$ORG" --partner-name "$PARTNER"

When it finishes, download output/report.html with Actions → Download file and open it in a browser. The CSV files beside it are described under What the run writes.

Organization

Run these in the management account, in the same window. One stack creates the role in the management account and, through a StackSet it contains, in every member account, now and as accounts join. The management account needs its own copy because a StackSet cannot deploy to the account that owns it; the template does both.

Not yet confirmed against a real organization Every line has been checked against the AWS CLI's syntax and run against a recording fake, the template has been checked with cfn-lint, and the collector's organization mode has been run against a simulated organization. These parts have not yet run in a real AWS organization: the StackSet inside the stack, including that the deploy waits until the member roles exist and that deleting the stack removes it; the collector reaching members from a single sign-on login (in the one test organization, the login was not allowed to assume the member roles); and runs longer than an hour. Roles arriving in member accounts has run once, from a StackSet made with the role template, not from this stack. If a step fails, the line stops there and nothing after it runs.

2. Create the role in every account

This turns on StackSets for the organization (once), then deploys data_risk_assessment_org.yaml: the role in the management account with read access to the organization's structure and service control policies, and a StackSet aimed at the organization root that creates the same role, unchanged, in every member account. New accounts get it automatically. An account where the role cannot be created does not stop the others; it shows as "not assessed" in the report.

aws cloudformation activate-organizations-access && aws cloudformation deploy --stack-name DataProtectionReviewer --template-file data_risk_assessment_org.yaml --capabilities CAPABILITY_NAMED_IAM --parameter-overrides TrustedPrincipalArn="$ME" ExternalId="$EXT" RoleName="$ROLE" OrganizationRootId="$(aws organizations list-roots --query 'Roots[0].Id' --output text)" && echo "ExternalId: $EXT"

Keep the External ID it prints. It is not a secret, but a later run needs it. To limit the member roles to one organizational unit, replace the OrganizationRootId value with that unit's ID (ou-…).

To see which accounts have the role (each should be CURRENT):

aws cloudformation list-stack-instances --stack-set-name DataProtectionReviewer-members --query 'Summaries[].[Account,Status,StatusReason]' --output table

3. Run the assessment

python3 collector.py --external-id "$EXT" --role-name "$ROLE" --org-name "$ORG" --partner-name "$PARTNER"

Your sign-in needs permission to assume the role in the other accounts. Reaching a role in another account needs sts:AssumeRole in your own permissions as well as the role's trust. If the run says AccessDenied for every member, ask your administrator to add this statement to your permission set or IAM policy: {"Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::*:role/DataProtectionReviewer*"}. If the organization does not allow that at all, use Organization without sts:AssumeRole instead.

The same command as for a single account. The management account's role lists the organization; the collector then uses the same role name in each member account.

Organization without sts:AssumeRole (IAM Identity Center)

Use this when your organization does not let the person running the review assume a role in other accounts (the run or the preflight says AccessDenied on sts:AssumeRole for every member, and an administrator cannot allow it). Nothing here calls sts:AssumeRole. Instead, an IAM Identity Center administrator gives the reviewer a read-only permission set in each account, and the collector reads each account with it through the IAM Identity Center access portal, the same way the AWS CLI gets credentials after aws sso login. The permission set holds the same read-only policy as the role, with the same explicit Deny on data and on every write; SECURITY_REVIEW.md explains it. No IAM role and no StackSet are created by hand, and no External ID is needed.

Not yet confirmed against a real organization The template has been checked with cfn-lint and the collector's IAM Identity Center mode has been run against a simulated organization with a simulated access portal. It has not yet run against real IAM Identity Center. If a step fails, the line stops there and nothing after it runs.

1. Give the reviewer the read-only permission set (IAM Identity Center administrator)

Run this in CloudShell in the account where IAM Identity Center is administered (the management account, or its delegated administrator), in IAM Identity Center's Region. Change the name in quotes to the user name the reviewer signs in to the AWS access portal with. The line finds the IAM Identity Center instance and the reviewer, lists the organization's active accounts except the management account, and deploys data_risk_assessment_permission_set.yaml, which creates the DataProtectionReviewer permission set and assigns it to the reviewer in each of those accounts. It needs IAM Identity Center administration rights (create permission sets and account assignments) and read access to AWS Organizations; it creates no IAM role in the management account.

REVIEWER="name the reviewer signs in with"; read -r INST IDS <<< "$(aws sso-admin list-instances --query 'Instances[0].[InstanceArn,IdentityStoreId]' --output text)"; WHO=$(aws identitystore get-user-id --identity-store-id "$IDS" --alternate-identifier "UniqueAttribute={AttributePath=userName,AttributeValue=$REVIEWER}" --query UserId --output text) && MGMT=$(aws organizations describe-organization --query Organization.MasterAccountId --output text) && ACCTS=$(aws organizations list-accounts --query "Accounts[?Status=='ACTIVE' && Id!='$MGMT'].Id" --output text) && ACCTS=$(echo $ACCTS | tr ' ' ',') && aws cloudformation deploy --stack-name DataProtectionReviewerAccess --template-file data_risk_assessment_permission_set.yaml --capabilities CAPABILITY_AUTO_EXPAND --parameter-overrides InstanceArn="$INST" PrincipalId="$WHO" AccountIds="$ACCTS" && echo "DataProtectionReviewer assigned to $REVIEWER in: $ACCTS"

The management account is left out because assigning a permission set there needs IAM rights in that account; the report lists it as not assessed. To assign it to a group instead of one person, deploy the same template with PrincipalType=GROUP and the group's ID. To name the accounts yourself, set AccountIds to their IDs separated by commas.

2. Set up the reviewer's AWS CLI sign-in (once)

In CloudShell, or any shell with the AWS CLI version 2. It asks for the access portal's start URL and Region (shown on the portal's "Access keys" page), gives a code to approve in your browser, then asks for an account and role: pick the management account with the permission set you normally use there. That sign-in is used only to list the organization's accounts, names and policies; every account is read with the DataProtectionReviewer permission set. If you cannot open the management account, pick any account; the report then lists the organization-wide figures as not assessed.

aws configure sso --profile dpr --use-device-code

3. Run the assessment

ORG="Customer name"; PARTNER="Partner name"; aws sso login --profile dpr --use-device-code && python3 collector.py --sso-profile dpr --org-name "$ORG" --partner-name "$PARTNER"

It signs in (approve the code in your browser), then reads every account where the permission set is assigned to you. Accounts without it are listed as not assessed, never as protected or unprotected. To limit the run, add --accounts and the account IDs. Download output/report.html as for the other paths.

Steps 1 and 3 in one line, when the administrator is also the reviewer

What the run writes

Everything goes to the output/ folder. These files contain account IDs, resource names and tag values: keep them somewhere appropriate and share them no more widely than the report.

Optional settings for a second run

Record what the customer confirmed, compare with the first run, set recovery targets, or write a copy with names replaced by labels:

python3 collector.py --external-id "$EXT" --role-name "$ROLE" --org-name "$ORG" --partner-name "$PARTNER" --overrides decisions.csv --baseline previous/assessment.json --recovery-targets targets.json

--overrides reads a CSV or JSON file keyed by resource ARN (criticality, data_sensitivity, tier, or excluded with reason, owner and review_date). --baseline compares with an earlier assessment.json. --recovery-targets reads JSON by tier, for example {"1": {"rpo_hours": 1, "rto_hours": 4, "min_retention_days": 90}, "3": {"max_retention_days": 35}}; tiers 1 and 2 take a minimum retention, tier 3 a maximum, and anything left out keeps its default. --redact (with --redact-key key.csv to keep the mapping) replaces account, resource, vault and plan names with stable labels; check a redacted report before sharing it. --regions us-east-1 us-west-2 limits the Regions scanned; by default every enabled Region that holds resources is scanned.

If you cannot create a role in the management account

Some organizations let an administrator deploy a StackSet to the member accounts but not create an IAM role in the management account. This option fits that case. The roles go into the member accounts only, and the collector lists the organization with your own sign-in instead of a role. It uses the same read calls, but your sign-in is not limited by the role's explicit denies, so use the role in the management account (above) wherever you can. Sign in to the management account with read access to AWS Organizations; Cost Explorer and the organization's policies are read with your sign-in too, and show as not assessed where it cannot read them.

The management account itself is not assessed, because it has no role. The report lists it as not assessed, with the reason, so it counts as a gap in the totals, not as protected or unprotected. Do step 1 above, then:

aws cloudformation activate-organizations-access && aws cloudformation create-stack-set --stack-set-name DataProtectionReviewer-members --template-body file://data_risk_assessment_role.yaml --capabilities CAPABILITY_NAMED_IAM --permission-model SERVICE_MANAGED --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false --parameters ParameterKey=TrustedPrincipalArn,ParameterValue="$ME" ParameterKey=ExternalId,ParameterValue="$EXT" ParameterKey=RoleName,ParameterValue="$ROLE" ParameterKey=IsManagementAccount,ParameterValue=false && OP=$(aws cloudformation create-stack-instances --stack-set-name DataProtectionReviewer-members --deployment-targets OrganizationalUnitIds="$(aws organizations list-roots --query 'Roots[0].Id' --output text)" --regions "${AWS_REGION:-us-east-1}" --operation-preferences FailureTolerancePercentage=100,MaxConcurrentPercentage=100 --query OperationId --output text) && until S=$(aws cloudformation describe-stack-set-operation --stack-set-name DataProtectionReviewer-members --operation-id "$OP" --query StackSetOperation.Status --output text); [ "$S" != RUNNING ] && [ "$S" != QUEUED ]; do sleep 10; done; echo "Member roles: $S"

Then check the accounts as above. Members that are not in the StackSet, or where the role did not arrive, have no role: the run reads the others and lists those as not assessed (neither protected nor unprotected). The preflight passes once the role works in any one member. Run:

python3 collector.py --org-with-current-credentials --external-id "$EXT" --role-name "$ROLE" --org-name "$ORG" --partner-name "$PARTNER"

If the roles are in some accounts only, name the accounts to assess. This line takes them from the StackSet, and the others are left out and counted on the Inputs page:

python3 collector.py --org-with-current-credentials --accounts $(aws cloudformation list-stack-instances --stack-set-name DataProtectionReviewer-members --query "Summaries[].Account" --output text) --external-id "$EXT" --role-name "$ROLE" --org-name "$ORG" --partner-name "$PARTNER"

The same line works when the identity running the collector cannot read AWS Organizations at all, for example a dedicated reviewer role in a separate account. The collector then assesses the accounts you name and reads nothing from the organization. Organizational units, service control policies, organization backup policies, costs and multi-party approval are reported as not assessed, not as "none found". Use the account IDs from the StackSet's instance list, and make that reviewer role the TrustedPrincipalArn when you deploy. Accounts then show as numbers; add --account-names names.csv, a file with one account ID,name per line, to show names instead.

To remove it, use the organization removal line under "Removing access" to take the roles out of the member accounts, then aws cloudformation delete-stack-set --stack-set-name DataProtectionReviewer-members. Skip delete-stack, which has nothing to remove here.

Easiest: run this in CloudShell. It looks in every Region for what the assessment created, shows what it found, and asks before it removes anything. The local results and files are only deleted if you say so, and never while a role is still in AWS.

Or by hand. Single account, or the management account's stack:

If something goes wrong

Step 1 prints an error, or "Role will trust:" is empty

Looking up your role needs iam:GetRole. If that is denied, find the ARN another way and set it yourself, for example ME="arn:aws:iam::123456789012:role/YourRole". For single sign-on, aws iam list-roles --path-prefix /aws-reserved/sso.amazonaws.com/ --query 'Roles[].Arn' lists the roles behind each permission set. An IAM user's own ARN is used as is.

The role already exists, or a step is run again

Step 1 handles this before anything is created, so the usual answer is to run step 1 and the lines after it again:

  • The stack already exists (an earlier run): it is updated in place, keeping the role name it has. Nothing fails because the role exists. If nothing changed, CloudFormation says there are no changes and the line carries on.
  • A first attempt failed (the stack is in ROLLBACK_COMPLETE, which cannot be updated): step 1 removes that empty stack first. It holds no role.
  • A role named DataProtectionReviewer exists that no stack here created (made by hand, by a stack with another name, or by this stack in another Region): step 1 leaves it alone and names the new role DataProtectionReviewer- plus six letters or digits. The deploy and run lines use that name through $ROLE.

Step 1 makes a new External ID each time, so after running it again the old External ID stops working and the collector needs the new one, which the deploy line prints. To keep the old one, skip step 1 and set EXT, ORG, PARTNER, ME and ROLE yourself.

If the deploy still says a policy such as DataProtectionReviewer-Inventory already exists, a policy was left behind without its role: delete it, or set ROLE to another name and run the deploy and run lines again.

In an organization, step 1 checks the management account only. A member account that already has a role of that name shows as failed in the member list (step 2's check line) and as "not assessed" in the report; the other accounts are not affected. To cover it, pick a name no account uses, for example ROLE=DataProtectionReviewer2, and run steps 2 and 3 again in the same window. The roles in every account are replaced with the new name. The organization deploy line can also be run over a management-account stack made from the role template alone (same stack name); it should update that stack in place and add the member roles, which is part of what has not yet been confirmed.

The collector cannot assume the role

Check access before a full run:

python3 collector.py --preflight --external-id "$EXT" --role-name "$ROLE"

The External ID must be the one the stack was created with. Running step 1 again makes a new one; to keep the old one, set EXT=<your id> instead of running step 1, and set ORG and PARTNER again too.

Access denied when assuming a role, and the role exists

AWS gives the same access-denied answer in four cases, so the message cannot say which: the role is not deployed in that account, the External ID differs from the one in the role's trust policy, the role's trust policy does not name the identity you are signed in as, or your own identity is not allowed to call sts:AssumeRole on the role. The last is the one the role's template cannot fix: it is set on the person running the collector (their permission set, user or role policy, or a session policy). In the AWS console, the access-denied page's "View all policies for request" shows which policies were evaluated.

The report covers only one account, but I wanted the organization

The collector reads the organization only through a role created with IsManagementAccount=true, in the management account. The organization template always creates it that way; a single-account stack made from the role template alone does not. If it was created without it, it says "This account cannot list an organization" and assesses that one account. Run organization step 2 (it always creates the management role with it), then run again. To assess only the management account on purpose, add --single-account.

Credentials last one hour

The collector assumes the role for one hour per account, and a sign-in that was itself started from single sign-on or another role cannot be extended past that. A single account finishes well inside it. A very large organization run that goes past an hour can see later calls fail: the report lists those under Coverage gaps and shows the affected resources as not assessed, not as unprotected. Sign in just before you run.

Member accounts failed in step 2

The list-stack-instances line shows each account's reason. A common one is a service control policy that denies the Region CloudShell is in; switch CloudShell to an allowed Region, delete the stack with the removal lines, and run step 2 again. From a delegated administrator account instead of the management account, add StackSetCallAs=DELEGATED_ADMIN after --parameter-overrides in step 2 and --call-as DELEGATED_ADMIN to the list-stack-instances and removal lines.

Running from your own machine instead of CloudShell

You need the AWS CLI, Python 3.9 or newer, and the pinned AWS library: pip3 install "boto3==1.43.108". CloudShell needs none of this. The commands are bash; on Windows use WSL or Git Bash. If the collector fails with a TLS or certificate error behind a corporate proxy, run it with the system Python, or install python-certifi-win32 (Windows) so Python uses the operating system's certificate store.

Creating the role in the console instead

CloudFormation → Create stack → With new resources → Upload data_risk_assessment_role.yaml. Fill in TrustedPrincipalArn (the "Role will trust" value from step 1) and ExternalId (from step 1: echo $EXT), acknowledge IAM resources, and create. For an organization, upload data_risk_assessment_org.yaml instead, fill in the same two values and OrganizationRootId (from aws organizations list-roots), and turn on trusted access for StackSets first (CloudFormation → StackSets → Enable trusted access). Then run step 3 of either path.

What the role can and cannot do

The template includes an explicit Deny that no other policy attached to the role can override. Every permission and the reason for it is in SECURITY_REVIEW.md.

What an External ID is, and is not It stops a third party from tricking the collector into using this role on their behalf. It is not a password: AWS can record it in CloudTrail when the role is assumed. What protects the role is who it trusts (TrustedPrincipalArn) and the explicit Deny. Anyone who can edit the role could detach that Deny, so if it must be permanent, apply a permissions boundary or an SCP as well.
What is not supported The standard AWS partition only: AWS GovCloud (US) and the China Regions are not supported. Regions disabled for an account are skipped, and any Region that could not be reached is listed in the report under Coverage gaps.
